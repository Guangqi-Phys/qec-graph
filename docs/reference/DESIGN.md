# 从 CodeGraph 到 QEC 的 DataGraph 与 LemmaGraph

本文说明本工具的设计原则。它描述源码整理与查询层；是否支持某个命令、参数或语法，以本包 README 和实际诊断为准。数学陈述的规范化、数据含义审核与 Lean 证明仍需单独完成。

## 1. CodeGraph 提供了什么思路？

同名项目不止一个。以 colbymchenry 的 CodeGraph 为例，它先用 tree-sitter 解析源码，抽取函数、类等节点与调用、导入等边，保存在 SQLite，并解析引用目标，提供查询与面向 AI 的上下文。[1] 这种组织使 AI 可以直接查“谁调用这个函数”“修改会影响哪里”，无需每次重新阅读整个仓库。

对 QEC，可以复用“对象、关系、来源、查询”的结构，把代码符号换成定义、引理、码实例、矩阵、实验和证据。图的价值在于可查询的关系；可视化是它的一种展示方式。

## 2. 用一个带类型的图，提供三个视图

| 视图 | 主要节点 | 典型问题 |
|---|---|---|
| SourceGraph | 文件、章节、段落、定义、定理、证明、公式、图表 | 这段内容在原文哪里？引用指向谁？ |
| LemmaGraph | 定义、假设、引理、定理、证明、Lean 声明 | 需要哪些前提？哪些依赖已经明确？ |
| DataGraph | 码实例、矩阵、数据集、实验、指标、计算证据 | 这个数值描述哪个对象？输入和证据在哪里？ |

三者共享稳定 ID 与出处，不必分别部署数据库。一个表格属于 SourceGraph；表中描述的码实例属于 DataGraph；关于该实例距离的结论属于 LemmaGraph。可用“描述于”“支持”“形式化对应”等边连接。

还需要一个 schema 说明节点类型、字段含义和允许的关系。schema 告诉 AI “怎样解释数据”，图中的节点和边告诉 AI “实际有哪些数据及联系”。

## 3. 每种边都要有准确含义

| 关系 | 来源或解释 | 不能据此推出什么 |
|---|---|---|
| `contains` | 文件或章节包含某个片段 | 不表示数学依赖 |
| `references` | 明确的 `\ref`、`\eqref` 等引用 | 引用不一定是证明前提 |
| `cites` | `\cite` 指向书目键 | 不等于依赖该论文的全部结论 |
| `depends_on_declared` | 作者 `\uses` 或人工明确声明 | 不是 Lean 实际证明项依赖 |
| `depends_on_candidate` | 从文字或证明引用推测 | 必须保留待核对状态 |
| `proof_of_candidate` | 根据邻近位置推测证明目标 | 相邻不保证就是该定理的证明 |
| `proof_of` | `\proves` 或明确标注指定目标 | 只标明意图，不证明论证正确 |
| `formalizes` | LaTeX 结论与 Lean 声明的对应标注 | 声明存在不保证语义等价或证明完成 |

边应附提取方式、源位置和审核状态。普通引用、作者声明和自动推测分别保存，查询时让使用者选择包含哪些关系。

leanblueprint 已提供适合借鉴的标记：`\uses{...}` 列出使用的标签，`\proves{...}` 指明证明目标，`\lean{...}` 列出对应的 Lean 声明，`\leanok` 表示作者声称已形式化。其 `checkdecls` 检查声明名称存在；这些标记本身不能代替 Lean 构建、公理检查及语义对应审核。[2]

文献引用允许有环。只有选定的数学证明依赖子图才讨论无环性；不要把整个知识图谱强行当作 DAG。

## 4. 自动切分保留原文，领域整理另建记录

建议流水线为：读取入口和包含文件，解析结构，提取片段与标签，解析引用，生成图，再创建查询索引。

每个片段保留原始 LaTeX、相对文件路径、字符区间、行号与源文件哈希。字符位置与字节位置需要明确区分；源代码行号也不等于 PDF 页码。章节、引理、证明等可按类型归档，但它们仍通过 `contains` 与来源记录连接。

本项目采用 Python 与 pylatexenc 2.10。该库能返回宏、环境、分组等节点及位置，并允许配置已知宏和环境；官方明确说明它不替代完整 LaTeX 引擎。[3] 因此源码解析不执行任意宏展开，也不能保证还原所有条件编译、复杂自定义环境和动态编号。未识别内容保留在原文件中，诊断应显式输出。

结构抽取可以确定“这里是一个 lemma 环境”，却未必能确定它的全部隐含假设。表格切分也不能自动确定其中的 `d=12` 是精确距离、上界还是某种电路距离。

DataGraph 的领域记录因此采用单独的人工元数据文件（sidecar）：明确实体 ID、类型、指标定义、字段和证据，再关联到原文标签或片段。例如，把表格关联到某个 HGP 实例，同时注明所选校验表示、GF(2) 约定及距离证据类型。后续若增加自动数字抽取，应将识别结果保留为候选，不直接升级为已审核参数；本版没有实现数字语义抽取。

## 5. 身份、修订与人工补充

有唯一 `\label` 时，优先用“文档命名空间 + label”定位；不同论文中的同名标签不能合并。无标签片段用位置和内容指纹定位一次出现，不承诺其跨编辑稳定。重复标签、未解析引用与缺失文件应成为诊断或未解析节点，避免静默连接到错误目标。

源片段表示某个版本中的一段文字；规范化的 `claim_id` 表示整理后的数学结论。相似文字不会自动证明两个结论相同，需要明确的合并或对应记录。

人工补充独立保存在 sidecar，自动导入只重建派生输出。补充记录应绑定审核时的片段哈希；原文变化后将对应审核标为过期或待复核。ID 相同只表示身份延续，不表示旧证据仍适用于新陈述。

每次构建记录源文件、解析器、配置和元数据指纹。重新切分只更新索引与片段产物；人工修正和重要证据保持可追溯。增量更新是后续优化，先让完整重建得到确定且一致的结果。

## 6. 给 AI 的查询接口

| 接口 | 应返回什么 |
|---|---|
| `ingest` | 导入快照、节点边统计、诊断 |
| `search` | 相关节点、类型、来源与匹配内容 |
| `show` | 精确节点、原文、元数据、入边与出边 |
| `context` | 所选节点及有界的定义、引用、证明、数据上下文 |
| `deps` | 按关系类型筛选的依赖链及证据状态 |
| `impact` | 沿指定关系反向寻找可能受影响的节点 |
| `validate` | ID、来源区间、引用及输出一致性检查 |

这些接口可以先通过 CLI 和 JSON 使用，以后再包装成 MCP；AI 客户端仍需配置相应访问权限与调用方式。依赖查询只能报告已记录的关系，不能保证论文中的隐含依赖已经全部抽出；影响分析也只提供待复查范围。

目前原型围绕源码切分、结构关系和数据关联工作，不编译 TeX、不自动理解全部数学语义，也不生成或验证 Lean 证明。后续 LLM 抽取可增加假设、概念和依赖候选，但应保留来源、模型版本与待审核状态。
